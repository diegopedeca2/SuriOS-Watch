## 2. Contexto

El repositorio contiene dos proyectos Gradle independientes:

- PIP-SuriOS en la raíz;
- SuriOS Watch dentro de `watch/`.

Cada proyecto dispone de configuración propia, incluyendo `settings.gradle.kts`, `build.gradle.kts`, catálogo de versiones, Gradle Wrapper y propiedades Gradle. Esta estructura permitió iniciar ambos productos por separado, pero duplica mantenimiento y crea dos raíces técnicas dentro de un único ecosistema.

## 3. Problema

La estructura obliga a mantener por separado:

- dos Gradle Wrappers;
- dos catálogos de versiones;
- dos configuraciones raíz;
- dos conjuntos de propiedades;
- dos puntos de apertura y compilación;
- versiones potencialmente divergentes de plugins y herramientas.

Esto aumenta el riesgo de divergencias, errores de configuración, duplicación de mantenimiento y dificultad para ejecutar validaciones conjuntas.

## 4. Motivación y objetivo

El ecosistema está concebido para crecer mediante productos independientes que comparten documentación, identidad, principios arquitectónicos y procesos. Se adopta desde una fase temprana una única raíz Gradle para evitar consolidar infraestructura duplicada.

El objetivo es migrar a un único build Gradle multiproyecto que administre PIP-SuriOS y SuriOS Watch sin modificar comportamiento, diseño ni alcance funcional.

## 5. Alternativas consideradas

### A. Mantener dos builds independientes

Ventajas:

- no requiere migración inmediata;
- mantiene independencia total.

Inconvenientes:

- conserva toda la duplicación;
- facilita divergencias;
- dificulta validaciones e integración futura.

**Descartada como estructura definitiva.**

### B. Composite Build

Ventajas:

- conecta builds separados;
- mantiene cierto aislamiento.

Inconvenientes:

- conserva wrappers y configuraciones duplicadas;
- añade complejidad innecesaria para el tamaño actual;
- no aporta una ventaja suficiente frente a un multiproyecto sencillo.

**Descartada en la fase actual.**

### C. Build Gradle multiproyecto

Ventajas:

- un único Wrapper y catálogo;
- una única configuración raíz;
- apertura conjunta en Android Studio;
- compilación y validación desde una sola raíz;
- menor duplicación;
- mejor preparación para crecimiento futuro.

Inconvenientes:

- requiere migración controlada;
- puede afectar rutas y configuración;
- un error raíz puede afectar ambos productos.

**Aprobada.**

## 6. Decisión

Se adopta un único build Gradle multiproyecto para el ecosistema SuriOS. Los productos permanecerán diferenciados y funcionalmente independientes, pero serán administrados desde una sola infraestructura Gradle.

Los módulos mínimos serán:

- `app`, correspondiente a PIP-SuriOS;
- `watchface`, correspondiente a SuriOS Watch.

Estructura conceptual objetivo:

```text
WristOS/
├── app/
├── watchface/
├── docs/
├── gradle/
├── build.gradle.kts
├── settings.gradle.kts
├── gradle.properties
├── gradlew
├── gradlew.bat
└── .gitignore
```

La ubicación definitiva podrá ajustarse durante Sprint 002 siempre que exista una sola raíz Gradle y no se reintroduzcan builds independientes.

## 7. Principios obligatorios

- Existirá un único `settings.gradle.kts` en la raíz técnica.
- Existirá un único Gradle Wrapper.
- Existirá un único catálogo principal de versiones.
- Ambos productos seguirán siendo funcionalmente independientes.
- No se introducirán dependencias entre módulos sin necesidad aprobada.
- No se compartirán recursos o código solo para justificar el monorepo.
- La Watch Face conservará exactamente el resultado aprobado de Sprint 001.
- PIP-SuriOS conservará su comportamiento.
- No se añadirán funcionalidades.
- No se modificarán decisiones visuales ni requisitos.
- No se iniciará Ambient Mode, batería, pasos, Spotify o Wallet.
- La migración deberá ser reversible mediante Git.

## 8. Alcance técnico autorizado

La migración podrá afectar exclusivamente a:

- configuración Gradle raíz;
- `settings.gradle.kts`;
- `build.gradle.kts`;
- `gradle.properties`;
- catálogo de versiones;
- Gradle Wrapper;
- rutas y nombres técnicos de módulos;
- `.gitignore`;
- configuración necesaria para importar desde Android Studio;
- comandos documentados de compilación.

Podrá ser necesario mover `watch/watchface/` a una ubicación dependiente directamente de la raíz, por ejemplo `watchface/`. Sprint 002 deberá resolver la ruta concreta antes de ejecutarla.

## 9. No objetivos y fuera de alcance

Este ADR no autoriza:

- cambios funcionales o visuales;
- cambios en `watchface.xml`;
- actualización de `preview.png`;
- Ambient Mode;
- batería o pasos;
- Spotify o Google Wallet;
- refactorización funcional de PIP-SuriOS;
- módulos compartidos sin necesidad aprobada;
- cambios de identificadores sin necesidad técnica;
- actualización indiscriminada de dependencias;
- modificación del EDL o requisitos de producto;
- reorganización o eliminación de documentación histórica.

## 10. Consecuencias

### Positivas

- apertura del ecosistema desde una raíz;
- compilación mediante un Wrapper común;
- reducción de configuración duplicada;
- coherencia de herramientas;
- validación conjunta;
- mejor preparación para nuevos módulos.

### Negativas

- mayor impacto potencial de errores raíz;
- obligación de validar ambos módulos;
- adaptación de rutas;
- necesidad de diferenciar cuidadosamente el alcance de cada producto;
- migración inicial controlada.

## 11. Riesgos y mitigaciones

### Pérdida o modificación accidental

Mitigación: partir de un punto Git estable, no eliminar duplicados antes de validar y revisar el diff antes del commit.

### Rutas Gradle rotas

Mitigación: definir todas las rutas en `settings.gradle.kts` y compilar cada módulo y el conjunto.

### Divergencia de versiones

Mitigación: comparar catálogos y conservar versiones validadas; no actualizar dependencias salvo necesidad imprescindible.

### Alteración funcional accidental

Mitigación: prohibir cambios funcionales y visuales, limitar archivos afectados y comparar el comportamiento antes y después.

### Configuración local de Android Studio

Mitigación: aplicar una política de `.idea`, ignorar archivos locales no necesarios y validar desde la raíz Gradle.

## 12. Criterios de aceptación

La decisión estará correctamente implementada cuando:

- exista un único build, Wrapper, `settings.gradle.kts` y catálogo principal;
- `app` y `watchface` estén incluidos;
- Android Studio abra ambos módulos desde la raíz;
- ambos productos compilen por separado;
- exista compilación conjunta;
- se genere el APK de SuriOS Watch;
- la Watch Face conserve el resultado de Sprint 001;
- no existan cambios visuales o funcionales;
- no se hayan incorporado Sprints posteriores;
- los duplicados se retiren solo tras validar;
- Git muestre exclusivamente cambios autorizados;
- el propietario apruebe el resultado;
- exista autorización expresa antes del commit.

## 13. Validaciones obligatorias

- revisión de estructura;
- sincronización Gradle;
- compilación limpia de PIP-SuriOS;
- compilación limpia de SuriOS Watch;
- compilación conjunta;
- generación de APK cuando proceda;
- instalación en emulador;
- comprobación visual;
- comparación con Sprint 001;
- revisión de Git;
- ausencia de cambios funcionales.

La prueba física en Xiaomi Watch 2 podrá añadirse si el propietario la considera necesaria.

## 14. Plan de reversión

Antes de iniciar debe existir un commit estable. Si la migración falla:

1. No se compensará mediante cambios funcionales.
2. Se documentará el fallo.
3. Se detendrá la operación.
4. Se restaurará el último commit estable mediante el procedimiento autorizado.
5. Se revisará ADR o Sprint antes de reintentar.

No se dejará el repositorio parcialmente migrado.

ADR-001 permanecerá vigente mientras el multiproyecto sea la arquitectura más sencilla y mantenible. Solo se revisará por incompatibilidad demostrada, cambio estructural del ecosistema o sustitución expresa mediante una nueva versión o ADR.

## 19. Resultado esperado

Al finalizar Sprint 002, PIP-SuriOS y SuriOS Watch conservarán su identidad funcional, pero podrán administrarse, abrirse, compilarse y validarse desde una única raíz Gradle.
